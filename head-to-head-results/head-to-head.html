CTADL Import Head-to-Head

Every app in ~/apps imported twice: once with the current Rust/Ascent ctadl, once with the older Souffle ctadl 0.14.1. Import only — nothing was indexed. What follows is how much each tool wrote to disk and how much code it got back for it.

The current importer recovers 6.0× the IR statements while writing 1.8× less data to disk — 11× less storage per statement recovered. The two effects have separate causes. The extra statements come from disassembling each app's native libraries, which the older importer never looks at. The storage difference comes from the format: a binary IR plus gzipped facts, against uncompressed Datalog text plus a full decompilation of the app back to Java.

TikTok 46.1.3 carries a large share of that: the older tool recovered nothing from it, so all 147.92 M of the current tool's statements there are unmatched. Setting TikTok 46.1.3 aside, the remaining 13 apps give 3.3× the statements for 3.3× less stored data — the same shape, less dramatic.

How this was measured

  • Stored data is the sum of file sizes under each import directory — for the current tool that is the IR bitcode, gzipped pcode facts, Parquet source-info, and the .so/split files it carves out of the APK; for the older tool it is the uncompressed Datalog .facts files, JADX's decompiled Java, and the unpacked resources.
  • Statements are IR statements: for the current tool, the statements in every basic block of every imported function, summed over the artifact and all its sub-imports; for the older tool, the rows of StmtInMethod.facts. The two IRs are not identical, so treat this as a measure of coverage rather than an exact like-for-like count.
  • Native libraries. The current tool disassembles one ABI's .so files per APK through Ghidra and imports each as its own sub-import; 14 of the 14 apps got native sub-imports. The older tool has no equivalent path in its JADX front end.
  • TikTok defeated the older tool. On TikTok's base split, JADX ran for 24 hours and then died with OutOfMemoryError: Java heap space; the plugin followed with a JSONDecodeError on the truncated source map. It had written 5 GB of decompiled Java and 144 MB of facts, but only 2 statements. The JVM's default maximum heap is a quarter of RAM (~32 GB on this machine). A retry with -Xmx96g is still running; this report records the default-heap result.
  • App bundles. Eight of the apps are .xapk bundles. The current tool imports each split. The older tool's JADX front end produces an empty fact set for them without failing, so those rows read zero; the “unpacked” columns show it re-run on the splits extracted by hand.
  • Not every megabyte of .so is code. WhatsApp Business ships a 13.6 MB libs.so that Ghidra analyses in two seconds and that yields 25 statements — it is a data blob wearing an ELF header. Statement counts track recovered code, not input bytes.
  • Each older-tool import was measured and then deleted — keeping all of them would have needed roughly 300 GB. The current tool's store was kept.
